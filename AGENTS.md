# Repository Guidelines

## Project Structure & Module Organization

This is a small Python CLI project managed with `uv`.

- `chess-spy/chess_spy/`: application package.
  - `cli.py`: Typer command entry point.
  - `chess_com.py`: Chess.com public API client and PGN ingestion.
  - `database.py`: SQLAlchemy engine, session, metadata, and association table.
  - `game.py`, `position.py`: SQLAlchemy models.
- `tests/`: pytest tests. Keep network-free unit tests here.
- `chess-com-api/`: Bruno collection for manually exploring Chess.com API endpoints.
- `chess_spy.db`: local SQLite database generated by the app; do not treat it as source.

## Build, Test, and Development Commands

- `uv sync`: install runtime and dev dependencies from `pyproject.toml` and `uv.lock`.
- `uv run chess-spy USERNAME`: run the CLI against a Chess.com username.
- `uv run pytest`: run the test suite.
- `uv run black chess-spy tests`: format source and tests.
- `uv run black --check chess-spy tests`: verify formatting without changing files.
- `uv run flake8 chess-spy tests`: run lint checks scoped to project files.

The console script is configured in `pyproject.toml` as `chess-spy = "chess_spy.cli:app"`.

## Coding Style & Naming Conventions

Use Python 3.11+ syntax. Format with Black and use 4-space indentation. Prefer clear module-level functions and small classes over broad abstractions. Use `snake_case` for functions, variables, and modules; use `PascalCase` for model/client classes.

Avoid global side effects where practical. In particular, keep network calls and database writes explicit enough to test without hitting real services.

## Testing Guidelines

Tests use `pytest`. Name test files `test_*.py` and test functions `test_*`.

Prefer isolated tests with fake Chess.com responses and temporary SQLite databases. Do not rely on live Chess.com API calls for normal test runs. Add tests when changing PGN parsing, archive selection, FEN normalization, database schema behavior, or CLI import behavior.

## Commit & Pull Request Guidelines

Recent history uses short, imperative or descriptive commit messages, for example `Adding sqlalchemy dependency` and `Restructuring project to use uv instead of Poetry`. Keep commits focused and explain why when behavior changes.

Pull requests should include:

- A short description of the user-visible or developer-visible change.
- Test results, usually `uv run pytest`, `uv run black --check chess-spy tests`, and `uv run flake8 chess-spy tests`.
- Notes about schema changes, API behavior changes, or manual Chess.com testing.

## Security & Configuration Tips

Do not commit local databases, credentials, cookies, or API captures containing private data. Chess.com public API calls should use respectful request pacing and avoid unnecessary headers such as unsupported content encodings.
